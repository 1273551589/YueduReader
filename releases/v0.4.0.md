# YueduReader v0.4.0 — 规则引擎重写

**一句话**：把 Legado 兼容性从「能导入书源」修到「书源真的能搜到内容」。

这一版没有新页面，全部用在底层。因为不修这些，加再多 UI 也是空壳。

---

## 修掉的四个阻塞级缺陷

这四条的共性是：**书源在 Legado 里能用，在这里不能**，而且失败方式都是静默返回空，
用户只能看到「未取到内容」，完全不知道是引擎的锅。

### 1. Legado 默认选择器语法（`class.` / `id.` / `tag.` / `text.` / `children`）

以前整串直接丢给 `jsoup.select()`：

| 规则 | Legado 语义 | 以前的真实行为 |
|---|---|---|
| `class.odd.0` | class 含 `odd` 的第 0 个 | 找 `<class>` 标签 → **空** |
| `tag.a` | 所有 `<a>` | 找 `<tag>` 标签 → **空** |
| `id.main` | id 为 `main` 的 | 找 `<id>` 标签 → **空** |
| `text.作者` | 文字含「作者」的 | 找 `<text>` 标签 → **空** |

现在由 `RuleSteps` 解析成「访问器 + 参数 + 索引过滤器」，再交给求值层。
`class.x` 按 Legado 的语义走**子串包含**（`[class*="x"]`），能命中 `class="book-item"`。

索引全部支持：`.0`、`.-1`（倒数）、`!0`（排除）、`[1,3]` / `1:3`（闭区间）、`!0:2`（排除区间）。
越界返回空而不是抛异常 —— 书源作者常靠这个探边界。

### 2. `@` 链式逐级下钻

以前 `findAttrSeparator()` 只返回**第一个** `@`：

```
class.odd.0@tag.a@href
→ 选 class=odd.0，然后去读属性名为 "tag.a@href" 的东西
→ 永远空
```

现在按 `@` 切成 N 段，逐级过滤元素，只有**末段是取值符**（`text` / `html` / `href` /
`src` / `ownText` / `data-src` …）时才做字符串提取。

切分时会躲开这些位置里的 `@`：`##正则##`（邮箱正则 `[\w.]+@[\w.]+` 里就有）、
`{{变量}}`、引号/圆括号/方括号内部（`li[data-mail='a@b']`）。

顺带补齐了 `规则主体<js>脚本</js>` 后缀脚本：前段结果作为 `result` 注入 Rhino。

### 3. 相对地址没拼基地址

```kotlin
// 以前：直接拿 /s.php 去 new URL()
URL("/s.php")  →  host 为 null  →  "URL 无法解析：/s.php"
```

现在 `searchUrl` / `exploreUrl` / `tocUrl` / 章节地址 / 下一页地址，全部相对
`bookSourceUrl` 解析成绝对地址。这也顺带修好了 `tocUrl`——以前详情页取到
`/list/1.html` 就直接发请求，目录必然为空。

### 4. POST body 变量替换 + 字符集编码

以前只在 `searchUrl` 字符串上做 `.replace("{{key}}", ...)`，body 里的占位符原样发出去：

```
实际发出： s={{key}}&type=articlename
应该是：   s=fate&type=articlename
```

字符集问题同样致命：声明 `charset: gbk` 的源，以前只拿它来**解响应**，
请求参数一律用 UTF-8 百分号编码。GBK 站收到 UTF-8 编码的中文就是乱码，直接 0 条结果。

现在 `UrlTemplate` 统一处理：变量替换 → 按声明字符集百分号编码 → 拼基地址。
空格编成 `+` 而不是 `%20`（表单站认前者）。JSON body 不编码（否则引号会变 `%22`）。

## 体检从「HTTP 200 就算过」改成四段校验

以前只要请求成功、列表解析出东西就是绿标。实测结果：一堆绿标的源，
点进去目录是空的、正文是「请登录后阅读」。

现在四段必须**全部**通过：

| 段 | 判据 |
|---|---|
| 搜索 / 发现 | 书名 + 详情 URL **都非空** |
| 详情 | 书名 + 目录地址都非空 |
| 目录 | 至少 1 章「标题 + 地址」都有效，且地址是绝对 URL |
| 正文 | >50 字 + 中文占比 ≥15% + **未命中假正文特征** |

### 假正文识别

这是「绿标骗人」的主要来源。登录墙页面往往有几百上千字，
「够长就算过」的判据完全挡不住。

内置 14 条特征，分两类：

- **登录墙**（UI 显示「需登录或人机验证」，而不是「未取到正文」）：
  `请先登录后阅读`、`VIP用户登录后`、`本章节为VIP付费章节`、`余额不足`、`人机验证`、`访问过于频繁` …
- **非登录墙**（显示「未取到正文」）：`正文转码中`、`章节内容加载失败` …

⚠️ 有个反直觉的坑：**必须先判假正文，再判长度**。
「请先登录后阅读」只有 8 个字，如果先判长度会被归成「正文过短」，
用户永远不知道其实是需要登录。这个顺序在 `judgeContent` 里写死了，
并有专门的测试盯着。

长正文只在**开头 60 字**里找特征 —— 真正文里「请先登录」作为台词出现在
第 500 字很常见，在第 1 句基本就是墙。

### 四段结果在界面上摊开

以前只有一个绿标/红标 + 「卡在 toc」。现在四个小药丸并排：
`搜索` `详情` `目录` `正文`，通过的绿底、失败的橙底，下面一行给出失败原因。
用户一眼能看出是哪条规则要改。

## 网络层换 OkHttp

换的理由不是「更潮」：

- `HttpURLConnection` **不跨协议跳** redirect（http→https 会卡住），
  书源里这种跳转极常见
- 没有连接池复用，几十个源的并发抓取会反复握手
- 图片站要注入 `Referer`（Pixiv 必需），拦截器是唯一干净的做法

⚠️ 踩了一个坑记在这里：**千万不要手动设 `Accept-Encoding`**。
OkHttp 只在它自己设该头时才做透明 gzip 解压；一旦我们插手，它就不解压了，
`body.bytes()` 拿到压缩字节，转 String 全是乱码 → 目录/正文全部 `SelectorEmpty`。
实测：换 OkHttp 后 SF 书源 421 章目录直接变 0 章。删掉那行就好了。

## 智能分类引擎（为书城准备）

`BookClassifier` —— 纯函数、零网络、纳秒级。书城要并发分类上千本书，这个前提不能破。

以「书名 + 简介 + 书源 kind + 书源分组」为输入，本地关键词库加权投票：

| 信号 | 权重 | 理由 |
|---|---|---|
| 书名命中 | 5 | 作者起名会刻意点明类型 |
| 简介命中 | 2 × 命中数（最多 3） | 多个词命中说明真的像 |
| 书源 kind | 2 | **不可信**，只作修正 |

10 个一级分类：玄幻奇幻 / 武侠仙侠 / 都市言情 / 科幻末世 / 悬疑灵异 /
历史军事 / 轻小说 / 游戏竞技 / 成人向 / 其他。

### R18 判定宁可错杀

漏一本的代价是「用户没开 R18 也看到了」，这是最严重的产品事故。
误判成人的代价只是少显示一本。

- 命中成人词库 → `isAdult = true`，含 6 个细分标签（母子 / NTR / 百合 / 调教 / 人妻熟女 / 校园纯爱）
- **书源分组或 kind 带 R18/成人/18禁 标记 → 整源强制标成人**，哪怕书名简介完全干净
- 有成人信号但分类信号不足（加权分 < 5）→ 主分类直接归「成人向」

置信度用**绝对强度**而不是投票占比。占比有个致命缺陷：只有一种分类拿到票时
占比恒为 1.0，哪怕那票只来自一个 kind 标签 —— 用户看到「100% 确信是玄幻」
其实是瞎猜。现在按饱和权重算。

## 测试

**157 个用例全绿**（v0.3.7 是 81 个，新增 76 个）。

新增三个测试文件，都是**契约测试**而不是「跑通就行」：

- `LegadoSelectorTest`（29 个）：选择器语法逐条锁死，包含
  「`@` 在正则/属性值里不能被切」这类边界
- `RequestPipelineTest`（15 个）：起真实 HTTP 服务器验证
  相对地址拼接、POST body 替换、GBK 编码真的落到了请求上
- `StrictCheckTest`（10 个）：四段校验 + 假正文识别，
  含「登录墙不能报成未取到正文」这条
- `BookClassifierTest`（22 个）：分类与 R18 判定
